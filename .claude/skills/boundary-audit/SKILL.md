# 경계면 교차 검증

모듈 사이의 **연결**을 검증한다. 개별 모듈의 동작이 아니다.

## 왜 경계면만 보는가

이 프로젝트의 런타임 실패는 거의 전부 경계면에서 나온다. 양쪽이 각각 "올바르게" 구현되어 있는데 연결 지점의 계약이 어긋나는 유형이다. 이런 버그는 한쪽만 읽으면 **절대** 발견되지 않고, 문법 검사나 모듈 단위 테스트로도 잡히지 않는다.

실제 이력:

| 버그 | 경계면 | 원인 |
|---|---|---|
| `locator.click: Timeout 15000ms exceeded` | 감지 셀렉터 → 조작 셀렉터 | `.se-documentTitle` 로 감지 통과, `.se-documentTitle [contenteditable]` 로 클릭 → 대상 0개 |
| `글쓰기.bat` 실행 불가 | 파일 인코딩 → CMD 파서 | UTF-8 저장 + 파싱 중 `chcp` 변경 → 바이트 위치 어긋남, 줄 중간부터 실행 |
| `OLLAMA_TIMEOUT` 미문서화 | `src` 참조 → `.env.example` | 사용자가 조절할 수 있는 값인데 존재를 알 길이 없음 |

세 건 모두 "존재하는가?"로는 통과하고 "**양쪽이 같은 것을 가리키는가?**"로만 걸린다.

## 핵심 원칙: 양쪽 동시 읽기

경계면을 검증할 때는 **생산자와 소비자 파일을 같이 열어** 문자열 단위로 비교한다. 한쪽을 읽고 "이쯤이면 맞겠지"라고 판단하지 않는다.

| 검증 대상 | 생산자 | 소비자 |
|---|---|---|
| IPC 채널명 | `main.js` 의 `ipcMain.handle('채널')` | `preload.cjs` 의 `invoke('채널')` |
| 화면 API | `preload.cjs` 의 `exposeInMainWorld` 키 | `renderer/app.js` 의 `api.메서드()` |
| 에러 코드 | `src/*.js` 의 `throw new Error('코드')` | `main.js` 의 messages 맵 키 |
| 블록 타입 | `blocks.js` 의 `type: '...'` | `naver.js` 의 `typeBlocks`/`pasteBlocks`, `blocksToHtml` |
| 초안 shape | `content.js` 의 `normalizeDraft` 반환 | `blocks.js` 의 `buildBlocks` 입력, renderer 미리보기 |
| 폴더 키 | `config.js` 의 `PATHS` 키 | `main.js` 의 `openFolder(which)` |
| 환경변수 | `src` 의 `process.env.X` | `.env.example` 문서화, `envStatus()` |
| 이미지 슬롯 | `blocks.js` 의 `imageSlots` | `renderer/app.js` 의 이미지 생성 루프 |
| 셀렉터 | `naver.js` 의 셀렉터 배열 | 실제 네이버 DOM (모의 DOM 으로 대리 검증) |

## 1단계: 자동 대조 스크립트를 돌린다

```bash
node .claude/skills/boundary-audit/scripts/boundary-check.mjs
```

8개 경계면을 정규식으로 양방향 대조한다. 종료코드 0 = 전부 통과, 1 = 불일치 있음.

검사 항목: IPC 채널, 화면 API, 에러 코드 맵, 블록 타입 2종(naver.js / blocksToHtml), 폴더 경로 키, 환경변수 문서화, bat 인코딩.

### 리포트 읽는 법

**양방향으로 본다.** 한쪽에만 있는 것은 방향에 따라 심각도가 다르다:

| 상황 | 의미 |
|---|---|
| `preload.cjs 에만 있음` (IPC) | 핸들러가 없음 → 호출 시 런타임 실패. **즉시 수정** |
| `main.js 에만 있음` (IPC) | 죽은 핸들러. 의도적일 수 있음 (`selftest:done` 등) → 판단 필요 |
| `renderer 에만 있음` (화면 API) | `undefined` 호출로 즉시 실패. **즉시 수정** |
| `preload.cjs 에만 있음` (화면 API) | 미사용 API. 리스너(`onBoot` 등)는 정상 |
| `src 에만 있음` (에러 코드) | 영어 코드가 사용자 화면에 노출. **즉시 수정** |
| `main.js 에만 있음` (에러 코드) | 죽은 메시지. 해당 코드를 던지던 로직이 사라졌을 수 있음 |

`[건너뜀]` 은 양쪽이 모두 비어 있어 비교할 것이 없는 경우다. 통과가 아니다.

### 스크립트가 틀릴 수도 있다

정규식 기반이므로 코드 작성 스타일이 바뀌면 못 잡는다. 예를 들어 채널명을 상수로 뽑아 `ipcMain.handle(CHANNELS.write, ...)` 로 쓰면 스크립트는 0개로 읽고 `[건너뜀]` 을 낸다. **`[건너뜀]` 이 예상과 다르게 나오면 스크립트의 정규식을 의심하고 수동 대조로 교차 확인한다.**

## 2단계: 스크립트가 보지 않는 경계면을 직접 읽는다

**스크립트 통과로 끝내지 않는다.** 스크립트는 **알려진** 경계면만 본다. 이번 변경이 새 경계면을 만들었으면 스크립트는 아무것도 모른다.

직접 읽어야 하는 것들:

**응답 shape.** 스크립트는 채널 **이름**만 대조하고 주고받는 **데이터 모양**은 보지 않는다. `main.js` 의 핸들러가 `{ ok, saved, message }` 를 돌려주는데 `renderer/app.js` 가 `result.success` 를 읽으면 이름 대조는 통과하고 런타임에 `undefined` 가 된다. 핸들러의 `return` 문과 renderer 의 소비 코드를 같이 읽는다.

**초안 shape.** `normalizeDraft` 가 돌려주는 객체의 필드명(`title`, `sections`, `intro`, `outro`, `tags` 등)과 `buildBlocks` 가 읽는 필드명을 대조한다. 필드를 추가·개명하면 블록이 조용히 비어 버린다.

**폴백 경로.** 3중 AI 엔진과 5중 이미지 소스는 각각 독립 경로다. 한 경로를 수정하면 나머지가 여전히 동작하는지 확인한다. 특히 **키가 하나도 없는 상태**가 이 앱의 기본 사용 조건이다.

**숫자 계약.** 본문 15px, 소제목 19px, 1500자, 태그 10개, 소제목 5개 이상, 이미지 슬롯 = 1 + 소제목 수 + 1. 이 값들이 여러 파일에 흩어져 있으면 한쪽만 바뀌어 틀어진다.

## 3단계: 모의 DOM 셀렉터를 검증한다

`src/naver.js` 가 바뀌었으면:

```bash
node .claude/skills/naver-selector-repair/scripts/mock-editor-test.mjs
```

실제 네이버 DOM 은 로그인이 필요해 검증 불가다. 모의 DOM 6종 통과는 **회귀가 없다**는 뜻이고, 실제 동작 보장이 아니다. 리포트에서 이 구분을 유지한다.

## 4단계: 리포트를 세 갈래로 쓴다

**통과 / 실패 / 검증 불가** 를 구분한다. 검증하지 않은 항목을 리포트에서 생략하면 통과한 것처럼 읽힌다. 이것이 QA 리포트의 가장 흔한 거짓말이다.

```markdown
## 검증 리포트

### 통과
- [경계면] IPC 채널 14개 일치 (boundary-check.mjs)
- [경계면] 에러 코드 4개 ↔ 메시지 맵 4개 일치
- [셀렉터] 모의 DOM 6종 통과 — 회귀 없음

### 실패
- [경계면] `src/naver.js:467` 이 `title-box-not-found` 를 던지는데 `main.js` messages 맵에 없음
  증상: 영어 코드가 사용자 화면에 그대로 노출됨
  수정: `main.js:190` messages 맵에 한국어 안내 추가
  통보: app-shell 에게 전송함

### 검증 불가
- [셀렉터] 실제 네이버 에디터 — 로그인 필요. 모의 DOM 으로 대리 검증함
- [이미지] 캔버스 보정 품질 — renderer 환경 필요. app-shell 에 앱 구동 확인 요청함
- [네트워크] 이미지 소스 응답 — 이 환경에서 외부 호출 차단됨
```

### 실패 항목은 파일:라인 + 수정 방법까지 쓴다

"뭔가 이상합니다"는 쓸모가 없다. 담당 에이전트가 바로 고칠 수 있는 정보를 준다.

### 경계면 이슈는 양쪽 모두에게 알린다

한쪽만 고치면 반대쪽이 다시 깨진다. 예를 들어 블록 타입 불일치는 `content-engine`(생산자)과 `naver-automation`(소비자) 양쪽에 통보한다. 어느 쪽이 옳은지 모르겠으면 임의로 정하지 말고 양쪽에 계약 확인을 요청한다.

## 5단계: 점진적으로 검증한다

전체 작업이 끝난 뒤 1회만 검증하면 버그가 누적되고, 초기 불일치가 후속 수정에 전파되어 수정 비용이 커진다. **각 에이전트가 수정을 끝내는 즉시** 그 영역과 인접 경계면을 검증한다.

| 수정된 영역 | 즉시 검증할 경계면 |
|---|---|
| `src/naver.js` | 에러 코드 맵, 블록 타입 소비, 모의 DOM 셀렉터 |
| `src/blocks.js` | 블록 타입 3소비자, 초안 shape, 숫자 계약(크기·색) |
| `src/content.js` | 초안 shape, 3중 엔진 폴백, 글자수·태그 수 |
| `src/images.js` | 이미지 슬롯 수, 키 없는 상태 동작, IPC 응답 shape |
| `main.js` / `preload.cjs` | IPC 3단 전체, 화면 API, 에러 코드 맵, 폴더 키 |
| `글쓰기.bat` | bat 인코딩 (CP949, chcp 없음) |
| `.env` / `config.js` | 환경변수 문서화, `envStatus()` 키 |

## 새 경계면이 생기면 스크립트에 추가한다

수동으로 2회 이상 대조한 경계면은 스크립트에 넣는다. 같은 검사를 세 번째로 손으로 하고 있다면, 그것은 번들링 대상이라는 신호다.

`scripts/boundary-check.mjs` 의 `check()` 헬퍼를 쓴다 — 양쪽 배열, 양쪽 라벨, 불일치 시 보여 줄 `note` 를 넘기면 양방향 대조와 출력을 처리한다. 추가한 검사는 **현재 코드에서 통과하는지 먼저 확인한다.** 통과하지 않으면 실제 결함을 찾은 것이거나 정규식이 틀린 것이고, 둘 중 어느 쪽인지 확인한 뒤 진행한다.
